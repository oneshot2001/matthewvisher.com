The problem in the field

Most of what I learned about video evidence comes down to one question: can you prove where it came from and that nobody touched it? For twenty-one years that question was about footage. Now agents are reaching for the cameras themselves. An agent that can pull a snapshot or swing a PTZ head is an operator, and the record of what an agent did is usually a log line inside the same system that did it. Edit the log and nothing notices.

Why the usual answers fail

ONVIF is the industry standard, and it is a swamp of SOAP, profiles, and vendor quirks. The quick fix is a thin wrapper that hands a model the raw camera API and puts the policy in the prompt. That leaves two holes. The agent can do anything the credential can do. And the check that stopped it lives nowhere. A gate that fires without leaving a record can't prove it ever fired.

What I built

An MCP server over stdio. The tools are list_cameras, get_snapshot, ptz_move, ptz_preset, get_receipts, and commission_plan / apply / verify. Policy is per agent and fails closed: a tool allowlist, a camera allowlist, and PTZ step bounds. An agent the policy doesn't name gets nothing. No secrets are written to disk; credentials are resolved at startup from a local store.

How it works

Every call, allowed or denied, appends a receipt to a JSONL file. Each receipt carries the hash of the one before it and an ed25519 signature. Frames are content-hashed, so a snapshot can be tied to the receipt that produced it. Running with --verify walks the chain, and if one byte has changed it names the exact sequence number. This is what a denied call looks like on disk:

{
  "seq":       41,
  "ts":        "2026-08-20T21:04:17.512Z",
  "agent":     "agent:research-bot",
  "tool":      "ptz_move",
  "camera":    "yard",
  "decision":  "deny",
  "reason":    "camera not in allowlist",
  "prev":      "sha256:…c04d",
  "sig":       "ed25519:…8Qf1"
}

Since August 15 the receipts are wire-conformant with Agent Action Receipts, and AAR's independent verifier checks them. Under the one tool contract there are two transports, AXIS VAPIX over HTTP CGI and ONVIF SOAP, picked per camera. The SOAP is hand-authored. I claim no ONVIF conformance.

Where it stands

Version 0.1.0, experimental, tested against the three AXIS cameras on my own bench. Two things I measured rather than read: on AXIS OS 12.9.57 the admin account works for ONVIF over digest auth, while older 12.x firmware needs a separate ONVIF account. RelativeMove pan maps to degrees divided by 360 exactly; tilt and zoom are approximate. No non-AXIS hardware has been tried. The server signs with one key, not one per agent. It went out on Show HN on August 20, 2026.

What's next

Per-agent signing keys and a signed policy file, clip export, non-AXIS ONVIF hardware, and alignment with the MCP 2026-07-28 stateless revision. A side-ship came out of this work: vapix-openapi, an MIT-licensed OpenAPI description of the fifteen VAPIX paths I needed.
